# Master Backlog

> [!IMPORTANT]
> ## 当前权威私人全自动落地目标
>
> 本节是当前最高优先级产品决定，覆盖本文下方的“冻结产品主线”、P0/P1/P2 和历史 Epic 中与之冲突的路线或措辞。当前落地是**私人使用的商业级软件**，不是当前销售或公开发行版本。
>
> - 公开行情不要求用户配置交易 API，由系统自动采集。
> - 人的唯一配置动作是提供明确用于 Testnet/Sandbox 的交易 API 凭据；交易 API 仅用于账户私有数据和交易操作，不用于公开行情采集。
> - 启动后，Market、Research、Strategy、Risk、Execution、Recovery、Audit Agents 构成全自动闭环，不创建 `approve`、`reject`、`revoke` 或 L2/L3 人工审核流程。
> - 无法证明安全、能力未知、数据陈旧、配置不完整或执行状态不确定时，系统必须自动拒绝、隔离或暂停，并留下事实审计记录，不得转交人工审批作为继续执行条件。
> - 审计只记录已发生的事实、输入、决定、理由、状态变化和结果，不承担授权或审批职能。
> - Mainnet 继续禁用。当前桌面 Binance API 被视为 Testnet 假钱环境，且已明确授权系统执行自动 smoke；本文不代表 smoke 已执行或已通过。
> - `model_off` 成熟度的当前机器权威是 [`model-off-capability-maturity.json`](model-off-capability-maturity.json)。它保留 13 个产品能力条目并映射到 7 个运行时聚合；聚合不得删除条目或提升条目成熟度。任何核心条目的 `no` / `partial` 都明确表示未实现且未验收。
> - Teacher 保持冻结的未来、非核心能力，不进入当前实现或验收范围；Mainnet 保持 `disabled`，不得由任何成熟度或聚合结论隐式启用。
>
> 详细验收合同见 [`private-autonomous-deployment.md`](private-autonomous-deployment.md)。

### MO-01 当前权威口径

- 当前执行权威是私人、全自动、fail-closed 的 Testnet 闭环；不存在逐周期 `approve`、`reject`、`revoke` 或 L2/L3 人工审批队列。
- 13 个保留能力是成熟度核算单位；7 个聚合仅描述目标服务拓扑。聚合为 `partial` 时不能把其任一子能力升级为 `yes`，聚合中存在较成熟组件也不能把其他子能力升级为已实现或已验收。
- `yes` 只接受 JSON 中 `acceptance_scope` 明示的有限组件事实，不代表完整 Agent、完整聚合、端到端产品、真实 Testnet、Mainnet、商业发布或模型隔离验收。
- 本节与机器权威覆盖下方所有历史 `Review` 默认、人工审批和高风险人工审核措辞；下方内容继续保留用于历史追踪，不能恢复旧授权模型。

## 目标
以交易闭环为核心，把本地优先、多 Agent、RuntimeSnapshot、provider、风险、执行、回测、审计和通知能力统一成可验证的专业产品主线。

## 历史冻结产品主线（兼容追踪，非当前落地目标）

- 权威产品与事实映射：[`investor-professional-core-plan.md`](investor-professional-core-plan.md)
- P0（历史兼容）：加密 Testnet 的默认 `Review` 专业闭环；其中人工 Review/approve/reject/revoke 不是当前目标，现目标为 Testnet 全自动闭环；Mainnet 继续禁用。
- P1：先冻结全球股票与 broker 的 provider-neutral contract，再接授权数据和券商 sandbox/Paper。
- P2（历史兼容）：Teacher、课程、CRM、Telegram 和 WhatsApp 只消费可追踪事实；“高风险内容必须人工审核”不是当前目标，当前应由系统在无法证明安全时自动拒绝、隔离或暂停。
- 安全声明：本地秘密已有 DPAPI 保护；SQLite 全库加密未实现，不得对外宣称已完成。

本节仅保留为历史兼容和工程追踪入口，不再覆盖顶部“当前权威私人全自动落地目标”。下方历史 Epic 同样不得被解释为恢复人工审批或当前销售/公开发行路线。

## P0

### Epic 1: Local Only 可运行
- 依赖: 本地配置、运行时真相、禁网/禁云策略
- 负责角色: 产品负责人、平台工程、桌面端负责人
- 验收标准: 离线可启动、可登录、可进入主界面、核心链路不依赖外部服务
- 并行边界: 可与品牌决策、插件目录整理并行；不可与任何云依赖上线并行

### Epic 2: Agent 角色目录 / 权限契约
- 依赖: Agent 角色定义、技能白名单、执行边界
- 负责角色: 产品负责人、Agent 架构师、风控负责人
- 验收标准（历史兼容措辞）: 角色清单、权限矩阵、可执行动作、禁止动作和自动授权边界全部可追踪；旧“审批边界”不代表人工 approve/reject/revoke 或 L2/L3 审核，这些均非当前目标
- 并行边界: 可与 RuntimeSnapshotV1 并行；必须先定契约再接执行

### Epic 3: 动态市场选择器
- 依赖: 市场目录、交易所适配、运行时状态源
- 负责角色: 产品负责人、行情负责人、前端负责人
- 验收标准: 可按交易所/品种/状态动态切换市场，且 UI 与运行时一致
- 并行边界: 可与 Agent 权限契约并行；依赖运行时快照口径统一

### Epic 4: RuntimeSnapshotV1
- 依赖: 运行时状态模型、账户/持仓/订单/风控/市场摘要
- 负责角色: 平台工程、数据负责人、前端负责人
- 验收标准: 单一快照足够驱动 UI 展示与审计追踪，不再依赖散落状态
- 并行边界: 可与动态市场选择器并行；必须先冻结字段口径

## P1

### Epic 5: 真实订单 / 持仓 UI
- 依赖: RuntimeSnapshotV1、订单与持仓读取接口
- 负责角色: 前端负责人、执行负责人
- 验收标准: UI 可稳定展示真实订单、持仓、状态变化与异常
- 并行边界: 可与插件目录整理并行；需等待快照字段稳定

### Epic 6: 本地优先 LLM 治理
- 依赖: 本地模型接入、上下文预算、调用审计
- 负责角色: Agent 架构师、平台工程、风控负责人
- 验收标准: 本地优先、可降级、可审计、可限额
- 并行边界: 可与真实订单 UI 并行；不可绕过 Agent 权限契约

### Epic 7: 插件 Phase 0 目录化
- 依赖: 插件清单、版本信息、加载约束
- 负责角色: 平台工程、插件负责人
- 验收标准: Phase 0 插件可发现、可分类、可禁用、可追踪
- 并行边界: 可与品牌决策并行；需对接权限契约但不改执行主链

## P2

### Epic 8: 品牌 Logo 决策
- 依赖: 品牌方向、视觉语言、命名一致性
- 负责角色: 产品负责人、设计负责人
- 验收标准: Logo 方案完成决策，但不直接进入工程实施
- 并行边界: 可完全并行于技术主线；仅作为决策节点

### Epic 9: 运营与扩展
- 依赖: P0/P1 稳定交付
- 负责角色: 产品负责人、增长负责人、运营负责人
- 验收标准: 形成后续版本的商业化包装、指标面板和试点计划
- 并行边界: 必须晚于 P0 完成后再展开

## 主依赖顺序
1. Local Only 可运行
2. Agent 角色目录 / 权限契约
3. RuntimeSnapshotV1
4. 动态市场选择器
5. 真实订单 / 持仓 UI
6. 本地优先 LLM 治理
7. 插件 Phase 0 目录化
8. 品牌 Logo 决策

## 统一原则
- 先定契约，再做页面。
- 先本地可运行，再谈扩展。
- 先统一状态，再做展示。
- 先治理权限，再开放 Agent。
